# Where every dataset in this project comes from

The trajectory generator covers the **Yangon FIR (ICAO region VY, Myanmar)**.
Four sources feed it. This document says which file comes from where, what it
is trusted for, and how to refresh it.

**Status as of 2026-09-29:** all navdata comes from one AIXM 5.1.1 export on
AIRAC **2609** (valid 03 Sep – 01 Oct 2026). See [Currency](#currency) below.

The project was originally built for the Bangkok FIR (VT). The Thai AIP scrape,
DFD layers, sector corrections, holdings, dummy traffic and CAT062 reference
table have been removed; only the Thai APM performance dataset (source B)
remains, deliberately.

---

## At a glance

| Source | What it authoritatively provides | Refreshable? |
|---|---|---|
| **A. AIXM 5.1.1 export** (SWIM, VY 2609) | Waypoints, navaids, airways + direction, airports/runways, SID/STAR/approach procedures, airspace polygons, P/R/D areas | Needs your own export (licensed) |
| **B. Thai APM** | Climb/descent **rates** per aircraft type | Regenerated by Thai APM |
| **C. VY track/FPL sample** | Real VY traffic (dep/dest/type/RFL/time + 3 crossing fixes) | Local export |
| **D. Operational assumptions** (in code) | Speed schedules, service ceilings, separation minima | Hand-maintained |

## A. AIXM 5.1.1 — the Yangon FIR export

`aixm_export_2609_VY_v5.1.1.xml` (7 MB, repo root), exported from the SWIM
catalog for VY 2609: 1 783 selected features, 3 546 after reference closure.

> **Licensing.** Navigraph/Jeppesen-derived commercial data. Internal and
> demonstration use only, **not for redistribution** — which is why the XML is
> gitignored while the layers built from it are committed, so the app runs from
> a clean clone. Refreshing needs your own copy of the export.

Every script defaults to that input and to the committed output location, so
each runs with no arguments. Nothing reads the XML at runtime.

| Script | Reads | Writes (under `web/public/data/`) |
|---|---|---|
| `ingest_aixm_route_segments.py` | `RouteSegment` endpoints, direction, level band | `aixm_vy/route_segments.json` — 186 segments on 86 routes, 15 one-way |
| `ingest_aixm_airports.py` | `AirportHeliport`, `Runway`, `RunwayDirection`, THR centreline points | `airports/Airport_with_AP_Main_vy.csv` (48), `airports/runway_vy.csv` (96 thresholds) |
| `ingest_aixm_waypoints.py` | `DesignatedPoint` / `Navaid` positions + the two files above | `aip_VY.json` — 456 waypoints, 86 airways, 48 airports |
| `ingest_aixm_airways.py` | `route_segments.json` + `VOR` features | `aixm_vy/airway_segments_vy.geojson` (186), `aixm_vy/airway_vor_vy.geojson` (18) |
| `ingest_aixm_procedures.py` | SIDs, STARs, approaches and their transition legs | `aixm_vy/{sid,star,pbn,ils}_*.geojson` |
| `ingest_aixm_airspace.py` | `Airspace` volume polygons | `aixm_vy/airspace_boundaries.geojson` (FIR/CTA/TMA/CTR, 42), `aixm_vy/restricted_areas.geojson` (P/R/D/TRA, 110) |
| `extract_aixm_restricted_areas.py` | P/R/D/TRA activation timesheets + notes | `aixm_vy/pdr_activity.json`, `aixm_vy/prdt_areas_2609.csv` (110 areas) |

`ingest_aixm_waypoints.py` and `ingest_aixm_airways.py` consume the outputs of
the two scripts above them, so run the table top to bottom.

### A1. `aip_VY.json` — the enroute network

Despite the name this is **not an AIP scrape**: it is built entirely from the
AIXM export, in the same shape as the retired Thai `aip_VT.json` so
`api/server.py` (`_aip()` / `_expand_airways`) reads it unchanged. Airway fix
sequences are stitched from the per-segment rows in `route_segments.json`; a
route whose segments do not form a single chain keeps each chain separate
rather than guessing a join. **This is what actually flies a filed route.**

### A2. Terminal procedures — `ingest_aixm_procedures.py`

Resolves each `ProcedureTransition` → `ProcedureTransitionLeg` chain to its
leg feature and takes the ARINC path terminator, course, altitude/speed limits,
turn direction, RNP and `flyOver`. AIXM has no waypoint description code, so
the IAF / IF / FAF / MAPt roles are **rebuilt** from each fix's position in its
transition. Output keeps the ARINC-424 "DFD" schema the navdata loader expects:

| File | Features |
|---|---|
| `aixm_vy/sid_waypoint.geojson` / `sid_line.geojson` | 283 / 86 |
| `aixm_vy/star_waypoint.geojson` / `star_line.geojson` | 206 / 77 |
| `aixm_vy/pbn_waypoint.geojson` / `pbn_leg.geojson` | 163 / 59 |
| `aixm_vy/ils_wp.geojson` / `ils_leg.geojson` | 814 / 276 |

Only 6 VY aerodromes publish coded procedures; the other 42 get a direct
departure/arrival. The `HM`/`HF`/`HA` hold legs inside these files feed the
holding patterns in `web/lib/holdings.ts`.

### A3. Airway direction and restricted airspace

`route_segments.json` is used by the PDR wrong-way-airway check
(`web/lib/pdr/airwayDirection.ts`) as well as by `aip_VY.json`.
`restricted_areas.geojson` supplies **where** each P/R/D area is and how high.
The 2609 export carries **no** activation data for any of the 110 areas, so
**when** an area is active comes from the AIP instead — see section A4.

### A4. AIP Myanmar — `web/public/data/VY_AIP/`

What the AIXM export lacks, taken from the AIP by `scripts/build_vy_aip.py`
(run from the repo root after the airspace/airport ingest):

| File | Source | Content |
|---|---|---|
| `transition_altitudes.json` | AIP Myanmar Table 3.6 (transcribed in the script; the AIP publishes it as an image) | TA (ft/m) and TL (FL/m) for 33 aerodromes, keyed by ICAO |
| `pdr_activity.json` | ENR 5.1 (`web/ENR-5.1.pdf`, AIRAC AMDT 01/2025) remarks column | Activation per area in the web app's `PdrActivityFile` shape — **read by the PDR check** |
| `restricted_areas.geojson` | AIXM geometry + ENR 5.1 | The 110 P/R/D features with `enr51_remark` and `activation` |

ENR 5.1 activation reading: a remark that mentions NOTAM → `NOTAM`, treated
as **inactive** until a NOTAM activates it (13 areas: all 8 D areas, R16,
R41, R46B, R52, R53); "Active: Permanent" / H24 → active every day
00:00–24:00 (40 areas); no ENR 5.1 row → `UNPUBLISHED`, assumed active
(R40A/B, drawn on the training-area chart only). The altitude readout
(`web/lib/transitionAltitude.ts`) switches to a flight level at the departure
TA while climbing and at the destination TL while descending.

## B. Thai APM — aircraft performance

`trajectory_sim/data/thaiapm_bada.sqlite` (+ an equivalent CSV export),
version `thaiapm-202607`, **66 aircraft types**, single ISA+15 variant.

Fitted to Bangkok FIR Mode-S DAP surveillance (`sur_air`, aggregate run 3193,
generated 2026-07-05). It is laid out like a BADA PTF but is **not a EUROCONTROL
product** — see `trajectory_sim/data/DERIVABILITY.md`. It is kept for the VY
build because no Myanmar-derived performance data exists; the climate
(approx. ISA+15) is a reasonable match.

What the simulator actually uses, and what it deliberately does not:

| Item | Used? | Note |
|---|---|---|
| Climb / descent **ROCD** (`rocd_nom`) | **Yes** | The p50 typical rate, used as-is even outside the brief's 1500–2500 fpm planning band |
| `rocd_lo` / `rocd_hi` | No | Percentiles across flights, **not** BADA mass bands, and inverted for climb |
| PTF TAS columns | No | Project-lead decision: the operational CAS/Mach schedule is used instead (source D) |
| Fuel columns / OPF coefficients | **Absent** | Not derivable from surveillance; there is no fuel model |

**Two consequences worth knowing.** Climb tables stop at the highest FL actually
observed in Bangkok, so a flight filed above that is *clamped* there rather than
extrapolated — an AT76 tops out at FL180 although its service ceiling is FL250.
And this dataset **superseded the BADA 3.16 PTF**; docstrings that still say
"BADA" are describing the shape of the table, not the source.

## C. VY track/FPL sample

`vy_2025_07_01_to_07_track.csv` (1 000 flights, repo root): dep/dest, callsign,
type, RFL, date/time, entry FL and the first three crossing fixes (`wp1..wp3`)
with WKB geometry. It imports into the web app as-is; the route is matched
against the real ATS network from `wp1..wp3`.

`scripts/make_vy_track_sid_star.py` writes `vy_2025_07_01_to_07_dummy.csv`: the
same rows plus `sid`, `star`, `approach`, `dep_rwy`, `arr_rwy`, matched against
the source-A procedures (falling back to the first published runway in
`runway_vy.csv`), so imported flights get a terminal procedure and a runway for
arrival sequencing.

## D. Operational assumptions — defined in code, not a dataset

These are **not** from any dataset and should not be presented as measured:

- **CAS/Mach speed schedules** (`performance.py`, 23 types) — "operational
  (airline LRC)". Nominal BADA-style speeds run faster than real ops, so the
  schedule is operational by choice.
- **Service ceilings** — manufacturer-published, per type.
- **CAS→Mach crossover altitudes** — BADA convention (~FL280 narrow-body).
- **250 kt below FL100** restriction.
- **Separation minima** — ICAO Doc 4444 §8.7.3: 3 NM in terminal areas, 5 NM
  elsewhere.

`icao-doc-4444-air-traffic-management.pdf` (ICAO PANS-ATM) is kept locally as the
procedural reference. It is copyrighted and gitignored.

## Generated inside this repo

Not source data — regenerate rather than edit:

- Everything under `web/public/data/` — rebuilt by the source-A scripts.
- `vy_2025_07_01_to_07_dummy.csv` — rebuilt by `make_vy_track_sid_star.py`.
- `api/_outputs/` — the export cache, rewritten on demand.

### Not modelled at all

- **No wind.** The trajectory model is zero-wind: `gs_kt == tas_kt`. A wind layer
  can be slotted in, but no weather data is ingested.
- **No fuel.** The Thai APM carries no fuel columns.

## Currency

| Dataset | Cycle | Effective |
|---|---|---|
| AIXM export + everything derived from it (`aip_VY.json`, `airports/*_vy.csv`, `aixm_vy/`) | 2609 | 03 Sep – 01 Oct 2026 |
| AIP Myanmar ENR 5.1 (`VY_AIP/pdr_activity.json`) | AIRAC AMDT 01/2025 | 10 Jul 2025 |
| AIP Myanmar Table 3.6 (`VY_AIP/transition_altitudes.json`) | as transcribed 30 Sep 2026 | — |
| Thai APM | `thaiapm-202607` | generated 05 Jul 2026 |

The PDR panel compares `pdr_activity.json`'s `validTo` against the current date
and shows a staleness banner once the cycle has expired. The API caches
`aip_VY.json` for the life of the process (`_aip()` in `api/server.py`), so a
running API has to be restarted to see a new cycle.

To move to a new cycle, drop the new export at the repo root and run (in this
order — later scripts read earlier outputs):

```bash
X=aixm_export_YYYY_VY_v5.1.1.xml
python scripts/ingest_aixm_route_segments.py    --input $X
python scripts/ingest_aixm_airports.py          --input $X
python scripts/ingest_aixm_waypoints.py         --input $X
python scripts/ingest_aixm_airways.py           --input $X
python scripts/ingest_aixm_procedures.py        --input $X
python scripts/ingest_aixm_airspace.py          --input $X
python scripts/extract_aixm_restricted_areas.py --input $X --output web/public/data/aixm_vy/prdt_areas_YYYY.csv
python scripts/build_vy_aip.py                  --enr51 web/ENR-5.1.pdf   # after an ENR 5.1 amendment too
```

Each script also takes an output flag (`--out`, `--output` or `--out-dir`; see
`--help`) to write somewhere other than the committed location. Once the new
layers are in, update the default input filename in each script.
